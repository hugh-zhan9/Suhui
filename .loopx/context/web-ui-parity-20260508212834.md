# Context: Web UI Parity

## Task Statement

Replace the current rough Desktop-hosted remote Web UI with a polished browser reader that is strongly consistent with the existing desktop app UI.

## Desired Outcome

The remote Web first screen should feel like the desktop RSS reader:

- left subscription/category column
- middle entry list
- right reading pane
- desktop-like density, typography, borders, hover states, selected states, empty/loading/error states
- management workflows exposed through modal/drawer surfaces instead of raw full-screen panels

- Clarify spec: `.loopx/specs/clarify-web-ui-parity-20260508211654.md`
- Master project context: `AI-CONTEXT.md`

## Known Facts And Evidence

- The repository is Desktop-only. The Web endpoint is an Electron-main-hosted remote access surface, not a separate Web/server product.
- Persistent truth remains local Postgres coordinated by Electron main. Remote Web must not write directly to DB.
- Prior full-Web-client build already added shared main-process application services, remote HTTP routes, and `@suhui/store/runtime`.
- Current remote UI is concentrated in `apps/desktop/layer/renderer/src/remote/remote-app.tsx`.
- `remote-app.tsx` currently contains a hand-built top header, view pills, simple list buttons, raw full-screen subscription/settings panels, and inline import/export textareas.
- Desktop app has established UI surfaces under:
  - `apps/desktop/layer/renderer/src/modules/app-layout`
  - `apps/desktop/layer/renderer/src/modules/subscription-column`
  - `apps/desktop/layer/renderer/src/modules/entry-column`
  - `apps/desktop/layer/renderer/src/modules/entry-content`
  - `apps/desktop/layer/renderer/src/modules/settings`
- Directly mounting the complete desktop shell is risky because `SubscriptionColumnContainer` and `MainDestopLayout` bring Electron/router-oriented concerns such as command bindings, player/update surfaces, network indicator, DnD, command panels, and desktop route assumptions.
- Remote runtime entry `apps/desktop/layer/renderer/src/remote/main.tsx` already hydrates remote stores and provides query/Jotai contexts.
- `packages/internal/store/src/runtime/client.ts` exposes remote-safe client methods for reading, subscriptions, refresh, read/unread, settings, RSSHub, import/export, and PDF.

## Constraints

- Keep Desktop-hosted remote architecture.
- Do not create a new top-level Web app or server package.
- Do not change the no-auth remote access model.
- Do not delete or broadly refactor existing desktop UI modules.
- Preserve existing application services, HTTP routes, and runtime client unless a narrow UI integration fix requires adjustment.
- Browser-safe degradation is acceptable:
  - browser download replaces native save dialog
  - native folder picker remains hidden
  - Electron menu, command palette, and desktop shortcuts are not first-pass requirements
  - settings expose Web-safe groups only

## Non-goals

- Window controls, tray, dock badge, open-at-login
- System notifications, system fonts, native folder picker, system proxy
- Electron menu / command palette / shortcut parity
- Desktop integration entrypoints
- AI, translation, summary online surfaces
- Player / corner media window parity
- New Web/server architecture
- Auth model changes

## Decision Boundaries

Implementation may decide:

- Rewrite `remote-app.tsx` in place or split it into remote-specific components.
- Reuse desktop components directly where browser-safe, or mirror their structure and tokens in remote components.
- Modal vs drawer details for management workflows.
- Toolbar/action menu details where desktop context-menu parity is too costly.
- Exact layout widths, breakpoints, spacing, and copy.
- Focused tests and screenshot verification approach.

Implementation must ask before:

- Changing remote server architecture.
- Introducing a new top-level Web/server app.
- Adding scoped-out desktop-native features.
- Changing no-auth remote access.
- Performing broad store/application-service rewrites beyond UI parity needs.

## Unknowns / Open Questions

- How much of desktop `entry-content` can be reused without pulling command, route, AI/translation, or source-panel dependencies.
- Whether desktop subscription list atoms can be used directly in remote without DnD/router assumptions.
- Exact screenshot tooling available in the build environment; Playwright or Browser Use can satisfy the wide-browser evidence gate.

## Likely Codebase Touchpoints

- `apps/desktop/layer/renderer/src/remote/remote-app.tsx`
- `apps/desktop/layer/renderer/src/remote/remote.css`
- new files under `apps/desktop/layer/renderer/src/remote/components/`
- `apps/desktop/layer/renderer/src/remote/main.tsx` only if providers or shell wiring need small adjustments
- focused tests under `apps/desktop/layer/renderer/src/remote/`
- only narrow runtime-client changes in `packages/internal/store/src/runtime/client.ts` if UI parity exposes a missing remote-safe operation
