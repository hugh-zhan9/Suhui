# 保留现有技术栈，以共享有界查询与渐进加载重构 Suhui 性能路径

## Abstract / 摘要

本提案保留 Electron、React、Drizzle、PostgreSQL 和现有持久化 schema，通过一个由 Electron main process 所有的共享条目查询边界，同时优化 Desktop 与 Desktop 托管的 Remote 浏览器入口。

核心变化是：条目列表只传输有界摘要页，正文按需获取；Desktop 启动不再全量 hydrate 正文；批量刷新只产生一次合并通知；Remote 先显示 shell，再独立加载初始数据；订阅侧栏在不损失排序、选择、右键、键盘和拖拽行为的前提下降低大列表渲染成本；非首屏能力从启动依赖图中延迟加载；打包规则明确排除已移除的内嵌 RSSHub runtime。

本提案不以技术栈替换或数据库改造换取性能。目标是在 400 订阅/1 万条目和 800 订阅/10 万条目两个已确认规模下，使首屏与列表交互成本不再随全库正文量线性增长，并保持现有阅读、未读、刷新、订阅和详情语义。

Design anchors: 本文是方向评审提案，具体 `D-*` 契约在配套详细设计中定义。

## Background / 背景与动机

当前性能瓶颈主要来自无界数据流，而不是 React、Electron 或 PostgreSQL 本身：

- Desktop IPC 按 feed 或全库返回完整条目，renderer 再过滤、排序和 `slice`；分页实际发生在传输之后。
- 启动关键 hydration 会读取所有可见条目，包括 `content` 与 `readabilityContent`，再写入 renderer store。
- 当前普通 Desktop/Remote 分页只使用 `publishedAt`，同一时间戳下缺少统一 tie-breaker。
- 批量刷新每完成一个 feed 都广播累计成功集合，renderer 对累计集合反复重拉，形成近似二次方的同步放大。
- Remote 在订阅、未读和 collections 三项请求全部完成后才挂载 React，任一慢请求都会决定白屏时间。
- 400/800 个订阅会放大侧栏的排序、订阅状态订阅和 DOM 渲染成本。
- Desktop 首屏模块图包含命令、集成、Shiki 等非首屏功能；Forge 忽略规则尚未明确排除本地遗留的 `resources/rsshub`。
- 仓库已有 agent 条目接口实现了摘要投影、稳定三字段游标和有界查询，证明现有 schema 足以承载共享查询方向。

诊断中生产 renderer 的 `shell_ready_ms` 约为 2051ms，而 snapshot restore 约为 81ms。证据指向启动依赖图、无界查询/传输和 hydration，而非 snapshot 本身。

因此，替换 UI 壳体、状态库或数据库不会自动消除全量查询、正文跨 IPC/HTTP 传输、刷新失效风暴和阻塞式 bootstrap。

## Goals And Non-Goals / 目标与非目标

目标：

- Desktop 与 Remote 使用同一套条目过滤、可见性、排序、游标和限制语义。
- 列表查询在 main process 内完成过滤、排序、投影和限制，分页路径不携带完整正文。
- Desktop 启动只恢复或查询有界摘要窗口，正文仅在打开详情时读取。
- 刷新后的主动同步为 O(N) 或更低，且不重复处理累计历史结果。
- Remote 在初始 API 未完成时已有可见 loading/error shell，并允许部分依赖独立恢复。
- 侧栏在 800 个订阅下保持现有交互语义，并避免无关节点反复渲染。
- 非首屏功能不进入关键启动依赖图。
- 生产构建和固定 fixture 可重复测量已确认的 P95 指标。
- 已移除的 RSSHub runtime 不进入 Desktop artifact。

非目标：

- 不更换 PostgreSQL，不改变持久化 schema、索引、迁移或数据库配置优先级。
- 不更换 Electron、React、Drizzle、router 或状态库。
- 不设计 Remote 认证、权限或公网部署能力。
- 不改变 RSS 阅读、排序选项、已读/未读、订阅或刷新结果。
- 不进行无测量依据的全仓依赖清理。
- 不重写整个 renderer store 或订阅侧栏信息架构。

## Proposal / 设计方案

### 1. Main process 成为唯一共享查询边界

在 Electron main 的 application 层形成统一 `EntryQueryService`。Desktop IPC、普通 Remote HTTP 和 agent 路径通过各自适配器调用该服务；renderer 不再从全量集合实现数据库级分页。

```text
Desktop renderer -> IPC adapter ----\
                                      -> EntryQueryService -> PostgreSQL
Remote renderer  -> HTTP adapter ----/

列表 -> EntrySummaryPage
详情 -> EntryDetail
```

共享语义包括：

- scope：单 feed、多 feed、All 和现有 active visibility 约束；
- read filter：未指定、已读或未读；
- 排序：`publishedAt DESC, insertedAt DESC, id DESC`；
- opaque keyset cursor：编码上述三字段；
- limit：默认 20，最小 1，最大 100，查询使用 `limit + 1` 推导 `hasMore`；
- 摘要投影：只返回列表和 store 合并所需字段，明确排除 `content`、`readabilityContent`；
- 详情：按 ID 返回现有完整条目；Desktop 保持“任意未删除条目”的深链语义，Remote/agent 保持 active visibility，不扩大跨表面可见性。

游标非法时拒绝请求，不退化成全量查询。scope 或 read filter 变化时客户端必须从第一页开始，不能复用旧 cursor。

### 2. 摘要和详情采用投影感知合并

renderer 继续保留规范化 entry store，但区分摘要写入与完整详情写入：

- 摘要写入只更新摘要字段，不得用字段缺失或 `null` 覆盖已缓存正文。
- 详情写入可补齐 `content`、`readabilityContent` 等详情字段。
- 打开未缓存正文的条目时，通过现有详情路径按需读取。
- 列表刷新、翻页或 SSE/IPC 失效后，已打开详情不能闪空。
- 本轮不引入新的持久化正文缓存。

### 3. Desktop 启动采用快照优先、有界校准

现有 startup snapshot 的摘要窗口保留。启动路径调整为：

1. shell 与 snapshot 尽早恢复；
2. DB 可用后加载订阅、feed、用户和未读等必要元数据；
3. 当前路由只请求首个摘要页，对 snapshot 做校准；
4. 其他页随滚动或路由切换按 cursor 获取；
5. 正文永不属于全库 entry hydration。

`shell_ready` 和 `interactive` 不等待全量 entry hydrate。snapshot 缺失、过期或损坏时显示现有空/loading 状态并请求第一页，不能回退到全量正文读取。现有 hydration barrier 的“用户写入优先”语义继续保留。

### 4. 刷新同步改为一次批次通知

刷新抓取、去重、写库和错误结果保持不变。单次逻辑刷新形成一个 ChangeSet：

```json
{
  "source": "manual-batch",
  "batchId": "opaque-id",
  "scope": "feeds",
  "feedIds": ["feed-1", "feed-2"],
  "refreshed": 2,
  "failed": 0
}
```

单 feed 兼容保留 `feedId`；Remote SSE 事件名继续为 `entries.updated`；Desktop IPC 通道继续为 `local-feed-refresh-completed`。批量刷新只在逻辑批次结束时发送一次合并通知，不在每个 feed 完成时发送累计成功集合。

renderer 立即 refetch 与 ChangeSet 相交的当前活动查询，非活动查询仅标记 stale；refresh 只合并失效 entries 与 unread，read/collection/subscription/import 按详细设计中的矩阵分别处理。重复或快速连续事件按 `batchId` 与 query key 合并。SSE 断线期间数据库仍是真相源，重连后校准当前视图。

### 5. Remote 采用非阻塞 bootstrap 状态机

Remote HTML 先提供轻量可见 shell；JavaScript 加载后立即挂载 React，不再在 `hydrateFromRemote()` 完成前阻塞 mount。

bootstrap 分成三个独立状态组：`/api/bootstrap` 原子返回 subscriptions/feed、unread、collections、settings/capabilities；当前 entry summary page 在 metadata 成功后独立加载；SSE connection 独立建立。任一状态失败都在已挂载 shell 中显示对应错误和重试，不卸载已成功区域。

指标定义固定为：

- shell first visibility：静态或 React loading shell 首次可见；
- initial data ready：metadata bootstrap 成功，且初始条目页已呈现或确认空状态。错误可见性单独计时，不能用快速失败通过 data-ready 门槛。

SSE 仍显式显示断线，不得把离线写入伪装成成功。

### 6. 订阅侧栏降低重算和 DOM 成本

侧栏优化以可测瓶颈为准，允许稳定 selector、memoized derived data、分段/虚拟渲染和只渲染展开分类。任何方案必须保持：

- 未读/字母排序及升降序；
- 当前选择、未读数字和分类展开状态；
- 右键菜单、键盘导航、焦点恢复；
- 拖拽排序和拖拽命中行为；
- 订阅新增、删除、编辑后的即时同步。

若虚拟化与现有拖拽/可访问性不能同时通过行为测试，则保留 DOM 结构，先采用 selector 与 memo 优化；不能为追求指标删除交互。

### 7. 首屏依赖按用户路径隔离

首屏只保留 shell、路由、当前列表和基础 provider。设置、命令面板、集成、发现、HTML/readability 处理、Shiki、编辑器和其他仅在特定动作发生时使用的模块，通过路由级或功能级动态导入延迟加载。

是否隔离某依赖，以 production build 模块图、初始 JS/CSS 大小和启动测量为依据；未进入关键图或无可测影响的依赖不纳入本轮清理。Remote 与 Desktop 分别设启动图预算，避免 Remote 静态引用 Desktop 完整功能集。

### 8. 性能与打包成为可重复验证契约

性能结论只来自 production build、固定 fixture、冷/暖启动和重复采样，不以开发模式单次测量代替 P95。

固定规模：

- 常规：400 subscriptions / 10,000 entries；
- 压力：800 subscriptions / 100,000 entries。

阈值：

- Desktop `shell_ready_ms <= 1.2s` P95；
- Desktop `interactive_ms - db_usable_ms <= 500ms` P95；
- feed/unread 视图切换到可用列表 `<= 300ms` P95；
- Remote shell first visibility `<= 800ms` P95；
- Remote initial data ready `<= 1.5s` P95。

查询验证记录生成 SQL、返回行数、投影字段、payload bytes 和执行时间。由于本轮不改 schema，若 10 万条目 fixture 无法达到目标，应记录证据并返回 `clarify/spec`，不得静默添加索引。

artifact 验证将“不得存在 `resources/rsshub`”作为硬性条件，同时确认 `app-update.yml` 等必需资源仍存在。

## Boundary Scenarios / 边界场景

| 场景                         | 设计处理                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------- |
| 空库、无订阅或 feed 无条目   | 返回空 page，`hasMore=false`；两端呈现现有空状态                             |
| `limit` 缺失                 | Desktop IPC 与 HTTP 都使用默认 20                                            |
| `limit <= 0`、非数字或超上限 | 返回稳定参数错误，不得 clamp 或触发无界查询                                  |
| cursor 损坏或版本未知        | HTTP 400、IPC typed error；不得静默从第一页续读                              |
| 多条目发布时间相同           | `insertedAt`、`id` 保证稳定顺序，无重复或遗漏                                |
| cursor 与新 filter 混用      | 客户端 query key 变化后重置分页；不承诺跨过滤器续页                          |
| 翻页期间插入新条目           | 当前 keyset 继续旧方向；收到 ChangeSet 后活动查询从第一页校准                |
| 未读列表中标记已读           | 本地即时更新；稍晚摘要不得回滚用户写入                                       |
| 详情已缓存后列表 refetch     | 摘要 merge 不覆盖正文                                                        |
| 详情 deleted 或失去可见性    | 保持现有 not-found 行为，不泄露正文                                          |
| 历史 `read=NULL`             | 继续按未读过滤，并在 summary 中规范化为 `read=false`                         |
| 1、10、50 feed 批量刷新      | 每批最多一次合并通知；重载次数为 O(N) 或更低                                 |
| 重复或乱序通知               | 合并失效，最终以数据库查询校准                                               |
| 批量刷新部分失败             | ChangeSet 只包含成功 feed；失败数和审计日志保留                              |
| Remote bootstrap 单项超时    | shell 保持可见；失败资源显示错误并可独立重试                                 |
| SSE 断线或错过事件           | 显示 disconnected；重连后主动校准当前视图                                    |
| DB 不可用                    | 不扩大本轮 DB 重试策略；不回退全量本地镜像                                   |
| snapshot 损坏                | 忽略并请求第一页，不阻塞 shell                                               |
| 800 个订阅侧栏               | 渲染/订阅成本受控，同时保持全部交互语义                                      |
| 旧 HTTP 调用                 | route/method/`data` 可继续解析；默认只返回首个摘要页，调用方须按 `page` 翻页 |
| 认证和权限                   | 不涉及 redesign；当前 LAN/VPN 边界不变                                       |
| 老数据和回滚                 | 无迁移；旧应用可继续读取同一数据库                                           |

## Rationale / 理由与取舍

推荐方案直接消除已测得的无界读取、正文传输和重复失效，改动集中在现有 application、transport adapter、renderer store 和 bootstrap 边界。它利用仓库已有 agent keyset 查询经验，不引入第二套数据所有权或运行时。

代价是列表与详情成为显式契约，renderer store 的 merge 语义更严格，且 HTTP 调用方必须消费分页 metadata。`/api/entries` 的 URI、method 和 `data` envelope 保持兼容，但无参数请求也只返回默认 20 条摘要；继续返回全量正文会保留原始资源耗尽路径，因此不提供 legacy 无界分支。仓库内 React Remote 与 fallback shell 与服务端同版本迁移。

| Alternative                           | Why Not                                                                     |
| ------------------------------------- | --------------------------------------------------------------------------- |
| Electron/React 改为 Tauri/Svelte/原生 | 不消除全量 SQL、正文传输、假分页和刷新风暴；迁移面远大于问题本身            |
| PostgreSQL 改 SQLite                  | 用户明确排除数据库设计变化；迁移也不能自动修复应用层无界数据流              |
| 仅增加数据库索引                      | 无法减少 IPC/HTTP payload、renderer 排序和正文 hydration；本轮也不改 schema |
| 仅做列表虚拟化                        | 可降低 DOM 成本，但数据仍全量查询、序列化和存储                             |
| Desktop 与 Remote 各自实现分页        | 过滤、可见性和排序语义容易漂移                                              |
| offset pagination                     | 刷新插入时更易重复/遗漏，深页成本随 offset 增长                             |
| 保留全量列表并 gzip/缓存              | 只缓解网络字节，不解决 DB、IPC、内存和失效成本                              |
| 新建 `/api/v2/entries`                | 当前可用 additive contract 兼容，新增长期版本会扩大维护面                   |
| 每个 feed 完成即发 delta              | 800 feeds 仍可制造事件风暴；批次 ChangeSet 更适合 UI 一致性                 |
| 重写整个 store                        | 超出性能目标；投影感知 merge 足以保护摘要/详情正确性                        |

## Compatibility / 兼容性

本提案对数据库和持久化数据完全兼容，没有 schema migration、backfill 或数据格式重写；旧应用可直接读取同一数据库。

用户可见的阅读、未读、排序、刷新结果、订阅管理和详情内容保持不变。Remote 更早显示 loading/error shell，是已确认的行为改进。

接口策略：

- Remote URI、HTTP method、详情路由和 `{data: [...]}` 主 envelope 保持。
- `/api/entries` 增加可选 scope、`read/unreadOnly`、`cursor`、`limit` 和必有的顶层 `page`；`data` 仍为数组。
- `limit` 缺失时默认 20，任何请求都不会返回无界全集。
- 列表不含 `content` 与 `readabilityContent`；详情继续通过 `/api/entries/:id` 获取。
- SSE 事件名不变；单 feed 保留 `feedId`，批量 `feedIds`/`batchId` 为 additive。
- Desktop IPC 可新增 page-oriented channel；旧 `db.getEntries` 只作过渡兼容，不得继续用于生产列表和 hydration。
- `/api/agent/entries`、CLI 行为和当前 agent response envelope 保持兼容，底层可复用共享查询。
- cursor 不持久化到数据库；非法或不兼容 cursor 由客户端从第一页恢复。

Remote API 是 Desktop 托管的产品内部表面，当前支持调用方均在仓库内并随应用升级。若实施前发现仓库外受支持调用方依赖全量正文或一次取完全集，必须返回 `spec` 决定版本化/迁移，不能恢复无界默认值。

## Operational And Security Impact / 运行与安全影响

运行影响：

- main process 从少量超大查询转为有界分页查询；总读取量随用户实际浏览增长，而非随数据库总量在启动时增长。
- renderer 内存和 IPC/HTTP payload 降低，但快速翻页会增加小查询数量，因此需要 limit 上限、请求取消和 query cache。
- 不增加后台服务、数据库实例、部署单元或迁移运维。
- refresh audit 延续现有 trace，并记录批次通知数、changed feed 数和活动 query refetch 数。
- 观测列表 query duration/rows/payload、详情补拉、Remote bootstrap 各资源耗时、SSE reconnect、bundle bytes 和 artifact exclusions。
- 性能失败时区分 DB execution、main serialization、transport、renderer commit 和 asset loading，不能只记录总耗时。

恢复与回滚：

- 查询失败不回退无界查询；返回明确错误并允许当前视图重试。
- Remote 部分 bootstrap 失败不清空已成功数据。
- snapshot 和 query cache 可丢弃重建。
- 无 schema 变化，应用代码回滚即可恢复。

安全影响：

- 分页摘要不传输正文，减少 Remote 无意数据扩散。
- cursor 只编码排序位置，不包含 SQL、连接信息或正文。
- limit 上限降低 LAN 接口的资源耗尽风险，但不替代认证或 rate limiting。
- Remote 当前绑定和认证边界不变，本轮不能被描述为完成安全加固。
- 错误响应不得包含 SQL、连接串、文件路径或正文。
- RSSHub 打包排除减少废弃运行时代码进入 artifact，不改变外部 RSSHub 网络权限。

## Implementation And Transition / 实现与过渡

过渡遵循以下兼容顺序，但具体文件、提交和命令由 `plan-to-exec` 决定：

1. 先用 characterization 固定共享查询、摘要/详情、cursor 和现有用户行为。
2. Desktop 与 Remote transport 接入同一查询语义，保留现有外部 route/envelope。
3. renderer 切到有界 store、非阻塞 bootstrap 和批次 ChangeSet 后，消除产品路径上的无界列表依赖。
4. 以 production fixtures 验证侧栏、启动图和 artifact 守卫，所有优化结论使用新的 P95 证据。

任何阶段不得使用“失败时全量读取”作为 fallback，否则会重新引入数据量相关卡顿。

## Open Questions / 待决问题

无阻塞问题。下列实现常量已在详细设计固定，不需要重新澄清：页大小、摘要 allowlist、ChangeSet shape、Remote `page` 字段和性能采样口径。

若性能门槛只能通过新增索引/schema 达成，或发现仓库外调用方无法兼容分页合同，则必须返回 `clarify/spec`，不得直接进入实现。

## Detailed Design Handoff / 详细设计交接

配套详细设计应把以下决定视为固定约束：

- 保留现有技术栈、PostgreSQL engine 和持久化 schema。
- main/application 层拥有唯一共享条目查询语义。
- 产品列表路径为有界摘要页，详情按需读取。
- 排序与 cursor 使用 `publishedAt + insertedAt + id`。
- Desktop 启动不得全量 hydrate 正文。
- refresh 使用批次级 ChangeSet，活动查询按影响范围校准。
- Remote 先显示 shell，再执行可部分失败和重试的 bootstrap。
- 订阅侧栏优化不得牺牲排序、选择、菜单、键盘或拖拽行为。
- Remote 现有 route、method、`data` envelope 和 SSE event name 保持兼容。
- 性能验证覆盖两个固定 fixture 和全部 P95 门槛。
- 不添加索引、迁移、认证 redesign 或全仓依赖清理。
