# 以统一的本地阅读数据层交付备份、聚类、规则、注释与阅读队列

Author(s): Suhui Team
Last updated: 2026-08-12
Status: Accepted
Discussion: 当前会话
Source requirements: `.loopx/intake/2026-08-12-local-reading-workflows/requirements.md`
Support lenses: `architecture-designer`, `sql-style`

## Abstract / 摘要

本提案在 Electron main process 所有的 PostgreSQL 数据面上新增五个相互兼容的本地域：版本化完整备份与本地 OPML、确定性内容聚类、入库后规则、逐篇笔记/高亮、独立稍后读队列。Desktop 与 Remote 只作为调用端，共享应用服务、事务和事件语义；完整备份在 Remote 尚无鉴权时只通过 Desktop 暴露。

完整备份采用可流式处理的单文件 NDJSON bundle；重复内容只聚类不删除；规则只默认处理新文章；笔记、高亮、标签和队列均绑定原始 `entryId`。所有用户数据可备份，派生聚类可重算，手动代表选择不可被重算覆盖。

## Background / 背景与动机

当前 JSON 导出只覆盖 feeds、subscriptions、collections 和已读 ID，不能恢复正文、设置或新用户数据；Desktop OPML 仍调用在线 Folo API。条目没有重复聚类、文章标签、规则、注释或独立阅读队列。若五项功能分别落地，备份格式、条目状态和刷新写入点会重复设计并产生迁移冲突。

## Goals And Non-Goals / 目标与非目标

目标：完全本地、可恢复、Desktop/Remote 一致；原始文章永不因聚类或隐藏而删除；用户创建的数据有稳定主键和备份契约。

非目标：云同步、多人冲突合并、在线 AI/向量聚类、通用规则 DSL、跨转载自动共享笔记、用 OPML 传输阅读数据。

## Proposal / 设计方案

1. main application 层新增 `backup`、`opml`、`dedup`、`rule`、`annotation`、`reading-queue` 服务；transport 不直接操作表。
2. 备份为 `.suhui-backup` NDJSON：首行 manifest，中间为按表记录，末行为 SHA-256 footer 与计数。导入先完整验证，再合并事务或完整替换事务。
3. 聚类使用版本化、确定性的规范化指纹：canonical URL 优先；否则规范化标题与正文摘要生成候选键。只在时间窗内比较候选，保留算法版本和匹配依据。人工代表项独立保存。
4. 规则条件为来源集合与标题关键词，动作是已读、加星、稍后读、标签和隐藏。规则在条目写入完成后以幂等应用记录执行；历史处理必须预览后确认。
5. 注释与队列均为条目级持久数据。高亮用 quote/prefix/suffix/source/offset 定位，刷新正文后重新定位；不确定时标记 orphaned。
6. 普通列表支持隐藏过滤和聚类折叠；搜索与管理查询可显式包含隐藏条目并展开聚类。

## Support Lens Checks / 专项设计检查

| Support lens            | Trigger                               | Design checks applied             | Result                                                         |
| ----------------------- | ------------------------------------- | --------------------------------- | -------------------------------------------------------------- |
| `architecture-designer` | 跨 Desktop/Remote、备份恢复与刷新流程 | 所有权、失败模式、恢复边界        | main application service 唯一写入语义；不新增部署单元          |

## Boundary Scenarios / 边界场景

- 损坏/未知版本备份：验证阶段拒绝，数据库不变。
- 合并重复记录：按稳定主键 upsert，不删除当前额外记录。
- 完整替换失败：事务 rollback；操作前安全快照保留。
- 重复刷新或规则重试：唯一应用键保证相同规则/条目只应用一次。
- 聚类误判：展开仍可见原始条目；用户可拆分或改代表，不丢状态。
- 正文变化：高亮重新定位；多处歧义或找不到时 orphaned。
- 已读与队列：互不联动；只有显式完成更新队列。
- 旧数据库：新增表为空，既有行为不变；聚类后台渐进回填。

## Rationale / 理由与取舍

| Alternative            | Why Not                                                |
| ---------------------- | ------------------------------------------------------ |
| 单个巨大 JSON          | 正文规模大时内存峰值不可控，难以校验与报告进度         |
| `pg_dump` 作为产品备份 | 环境依赖强、不可选择性合并、格式无法稳定跨 schema 版本 |
| 删除重复条目           | 破坏来源、逐篇状态和可恢复性                           |
| 在线 embedding 聚类    | 违背本地优先并引入隐私、可用性和运维依赖               |
| 将队列复用收藏或已读   | 无法表达积压、完成与长期收藏的独立语义                 |
| 规则直接修改订阅分类   | 单篇命中会意外影响整个来源                             |

## Compatibility / 兼容性

方案对既有 schema 和接口为 additive。既有条目、订阅、已读和收藏不改写；普通列表只在聚类/隐藏能力启用并产生数据后改变展示。备份 v1 导入器只接受自身支持的 major version。旧简易 JSON 导出继续可读为 legacy merge input，但不能作为完整替换源。

## Operational And Security Impact / 运行与安全影响

备份可能包含完整正文、笔记和隐私设置，默认不写日志内容，只记录路径、版本、计数和结果。临时文件使用权限受限的系统临时目录并在操作后清理。完整备份不经无鉴权 Remote 暴露；Remote 只提供不含阅读私密数据的 OPML。聚类和历史规则应用必须分批并报告进度，不能阻塞刷新事务。

## Implementation And Transition / 实现与过渡

先落 additive schema 与服务契约，再接入备份/OPML和条目入库钩子，随后交付 Desktop/Remote UI。聚类对历史数据渐进回填；规则只对启用后的新条目自动生效。旧 JSON import/export 保留兼容入口并标记为 legacy。
